# AQUARIUM — Fase cero

## Propósito

Establecer la línea base técnica, preparar un entorno local repetible y registrar las brechas antes de implementar requisitos funcionales. **QU4.pdf es la fuente normativa actual del alcance**, por decisión del usuario. El diagrama de despliegue guía la topología futura; las versiones V1/V2 y demás archivos sirven como antecedentes o referencias. Si QU4 contiene contradicciones internas, se registrarán para resolverlas sin cambiar el alcance por inferencia.

## Línea base acordada

| Área | Decisión |
|---|---|
| Backend | Laravel 12 y PHP 8.2+ |
| UI | React 18 con Inertia.js 1 y Vite |
| CSS | Tailwind CSS 3 |
| Datos locales | PostgreSQL 16 y Redis 7 mediante Docker Compose |
| Pruebas | PHPUnit; Selenium WebDriver y Apache JMeter según QU4 y el Plan de Pruebas Local |
| Futuro despliegue | Render para la aplicación; Supabase PostgreSQL y Storage. No se usa durante esta etapa local. |
| Pagos | Adaptador simulado; no se usan efectivo real, dinero, terminales ni APIs de pasarela. |

### Cambios de compatibilidad aprobados

- El 13 de octubre de 2026 se aprobó actualizar Laravel 11 a Laravel 12 con PHP 8.2, y registrar el cambio en la línea base. Laravel 11 terminó su periodo de correcciones de seguridad el 12 de marzo de 2026. La versión 12 mantiene soporte de seguridad previsto hasta el 24 de febrero de 2027 ([ciclo oficial de versiones](https://laravel.com/framework/docs/11.x/releases)).
- PHPUnit 11.5 y Collision 8.6 reemplazan PHPUnit 10.x de Main Work por compatibilidad con Laravel 12/PHP 8.2; se conserva el propósito de las pruebas, no se cambia su cobertura definida.
- El adaptador Laravel 1.3.3 incluye soporte de Laravel 12; se conserva Inertia 1.x como especifica Main Work. Se mantiene React 18.
- Main Work contiene dos incompatibilidades internas de línea base: OE-03 indica Python 3.12 y SQLite/PostgreSQL, mientras la pila de 5.4 detalla Laravel/PHP, React/Inertia y PostgreSQL; OE-08 menciona AWS, mientras las secciones 5.4-5.5 y el diagrama definen Render + Supabase. Se sigue la selección explícita del usuario: Laravel/React/Inertia, PostgreSQL, Render y Supabase; AWS/Python quedan registrados como contradicciones del documento, no como trabajo adicional aprobado.

## Estado del entorno y trabajo

- Esqueleto Laravel creado en `aquarium/`; dependencias instaladas: Laravel 12.69.3, Inertia Laravel 1.3.4, PHPUnit 11.5.57, Collision 8.9.5 y Predis 2.4.1.
- Configurados React 18, Inertia React 1.3.0, Vite 8.3.4 y Tailwind 3.4.19. La portada pública responsive sigue la referencia visual AQUARIUM.png: navegación, hero de búsqueda, categorías, especies recomendadas, clínica veterinaria y pie de página. Las fotos se guardan localmente dentro del proyecto.
- La portada y catálogo conservan la identidad visual de AQUARIUM.png y la navegación Inicio, Catálogo, Clínica e Información. Información presenta los servicios del negocio. El catálogo público consulta PostgreSQL local, busca por nombre, descripción, SKU y marca con Full Text Search indexado y permite combinar tipo de agua, marca y rango de precio. El carrito de sesión permite guardar productos para visitantes, confirmar pedidos como cliente con pago simulado, elegir Click & Collect o envío, recibir código de recolección y consultar pedidos en `/cuenta/pedidos`.
- Ruta de autenticación: registro e inicio/cierre de sesión con sesiones Laravel; contraseñas con hash y requisitos mínimos; perfiles básicos; asignación segura de rol `cliente` al registro público y middleware `role` para proteger rutas internas. Los roles base son cliente, administrador, almacenista, cajero POS y veterinario.
- Módulo de personal (solo administrador): consulta y búsqueda de empleados con rol, correo y teléfono, más alta de cuentas del personal. La primera cuenta de personal se crea desde consola mediante `aquarium:staff:create`, sin credenciales predeterminadas ni registro administrativo público. También permite editar perfil propio y solicitar restablecimiento de contraseña; el correo se escribe al log local, sin proveedor externo.
- Módulo de almacén (administrador y almacenista): alta de productos sin stock inicial, ubicación por pasillo/estante, recepciones con lotes/proveedor/fecha/costo, salidas de merma/mortalidad/ajuste y bitácora de cantidades anterior y posterior. El picking ordena artículos por ubicación; el retiro desactiva el producto y conserva su historial, y no permite retirarlo mientras tiene existencias.
- Módulo clínico: clientes reservan y consultan sus citas; la sucursal opera de 09:00 a 22:00 y la agenda admite reservas únicamente de 09:00 a 19:00 cuando el veterinario no tiene ocupado el horario. Cada veterinario puede tener una cita por hora exacta; el total concurrente depende de los veterinarios disponibles, sin un aforo global adicional configurado. El veterinario revisa datos de cliente/paciente, registra diagnóstico, mediciones y prescripción estructuradas y notas. El expediente PDF local restringido incluye SHA-256 y pie de página «SELLO NOM-151 · SIMULACIÓN LOCAL»; el propio pie aclara que no es sello oficial, firma electrónica, sello de tiempo ni certificación. El cargo/reembolso es simulado, sin API ni información de tarjeta.
- Módulo POS (administrador/cajero POS): venta de mostrador con cálculo del IVA 16%, bloqueo de concurrencia de producto, descuento atómico de existencias, comprobante de prueba y movimiento auditable. Tarjeta, transferencia y efectivo son simulaciones locales; en efectivo se valida el monto recibido y se calcula el cambio. `/pos/cierre-z` genera un corte por cajero/día, concilia fondo inicial, efectivo esperado y contado, registra diferencia y bloquea ventas posteriores de esa caja hasta el siguiente día. El efectivo simulado no implica efectivo real.
- Pedidos web: cantidades e inventario se validan en checkout; se crean orden, partidas, registro de pago simulado y movimiento de inventario en una transacción. Envío requiere destinatario, teléfono y dirección; estos datos se conservan como snapshot del pedido y solo el titular consulta su historial. El cliente ve pase QR y código de recolección; `qrcode.react` 4.2.0 lo genera como SVG dentro del navegador, sin enviar el código a un servicio. Almacén prepara Click & Collect en `/almacen/picking`; POS lee el código (teclado/escáner compatible) y confirma la entrega en `/pos/recolecciones`. Para envío, almacén registra preparación y salida con una referencia local ficticia que aparece en el historial del cliente. Cada transición conserva actor, estado anterior y estado nuevo en la bitácora de cumplimiento. No hay efectivo real, datos bancarios ni llamadas a APIs externas; no se conecta con una empresa logística.
- Vencimiento Click & Collect: `aquarium:orders:expire-pickups` identifica órdenes no recogidas durante 48 horas (configurable por opción). Ofrece `--dry-run`; al ejecutar, cancela la orden, marca el reembolso simulado, reingresa existencias y registra la bitácora. Vencimiento de pedidos y reservas del carrito están programados cada minuto en el scheduler local.
- Notificaciones de pedidos: al quedar listo para recoger, registrar salida local, confirmar entrega o vencer, el sistema guarda un aviso en la tabla `notifications`; el cliente los ve en `/cuenta/pedidos`. No se envían correos externos en la fase local.
- Reserva de carrito: cada sesión bloquea existencias por 30 minutos; checkout y operaciones de POS/almacén respetan las reservas activas. La orden registra aceptación de cuidado responsable y confirmación de advertencias de compatibilidad por especies vivas.
- Seguridad local adicional: registro de auditoría de solicitudes de escritura con usuario, ruta, estado, IP, identificador y hash SHA-256; no registra cuerpos, contraseñas o datos de tarjeta. Es una evidencia local y no equivale a una cadena inmutable ni a certificación NOM-151.
- Reporte local: `/admin/pruebas` presenta PHPUnit, PostgreSQL, Selenium y JMeter con sus historiales. Los resultados JSON, JUnit, JTL y dashboard se guardan en `storage/app/testing/`, excluido de Git. `scripts/test-postgres-local.ps1` usa una base segregada `aquarium_codex_test_YYYYMMDD`. JMeter 5.6.3 y Temurin JDK 21.0.12.1 están instalados en `tools/` con sus hashes verificados; Selenium WebDriver 4.51.0 está en dependencias npm. El perfil local de carga con Nginx + PHP-FPM se levanta por separado en el puerto 8080; `scripts/prepare-loadtest-image.ps1` arma una imagen con dependencias de producción para limitar el contexto.
- Humo HTTP local: `scripts/http-smoke-local.ps1` mide en paralelo Inicio, Catálogo y el filtro de agua salada; guarda JSON bajo `storage/app/testing/`. En la muestra del 19/10/2026 contra el servidor único conectado a PostgreSQL se obtuvieron 6 respuestas HTTP 200; latencia 2,193.49–2,204.62 ms (p95 2,204.62 ms). Es una muestra diagnóstica muy pequeña con el servidor PHP de desarrollo; no mide capacidad de 500 usuarios ni representa un servidor de producción.
- Se añadió `docker-compose.yml` con PostgreSQL 16 y Redis 7, almacenamiento local persistente y verificaciones de salud. Credenciales dentro de Compose solo son valores de desarrollo local; no deben reutilizarse en nube.
- `.env.example` y `docker-compose.yml` conservan PostgreSQL/Redis como configuración local objetivo. En esta máquina, `.env` (ignorado por Git) apunta a PostgreSQL/Redis en Docker. `scripts/prepare-local-sqlite.ps1` y `scripts/serve-local-sqlite.ps1` siguen disponibles para una demo de respaldo con SQLite; `scripts/serve-local.ps1` sirve el modo normal con PostgreSQL en `127.0.0.1`. Ambos servidores usan el router Laravel para entregar correctamente CSS/JS. `.nvmrc` fija Node 20.19.0, compatible con la versión actual de Vite; QU4 solo especifica Node 18/20. `scripts/php-local.ps1` carga PDO PostgreSQL, GD, ZIP e intl por proceso local.
- Entorno detectado: PHP 8.2 y Composer 2 instalados; Node 24.21 activo. Las DLL `pdo_pgsql`, `pgsql`, `gd`, `zip` e `intl` existen en XAMPP; `scripts/php-local.ps1` y `scripts/serve-local.ps1` las cargan por proceso sin editar el `php.ini` global.
- Las dependencias npm se instalaron; Vite se actualizó a 8.3.4 para eliminar sus avisos conocidos. npm aún reporta 7 avisos de dependencias del árbol de Tailwind 3 (5 altos, 2 moderados). Main Work especifica Tailwind 3; no se cambia a la versión mayor 4 sin autorización. Estos avisos quedan abiertos y deben resolverse o aceptarse explícitamente antes de publicar.
- Verificación más reciente: `npm run build` finalizó correctamente con Vite 8.3.4; PHPUnit ejecutó 54 pruebas y 622 aserciones en SQLite y la misma cantidad pasó en PostgreSQL aislado. Selenium aprobó 8 escenarios (Inicio/navegación, catálogo/filtro, autenticación para agenda y entrada a cuenta de cliente, reportes admin, almacén, POS y agenda veterinaria). JMeter sobre Docker/Nginx/PHP-FPM aprobó 6,421 solicitudes con 50 VU (rampa 10 s/duración total 30 s; promedio 195 ms, máximo 529 ms) y una corrida sostenida con 500 VU (rampa 60 s + 60 s adicionales a carga plena, duración total 120 s): 30,176/30,176 solicitudes correctas; promedio global 1,514.95 ms, p95 2,156 ms, máximo 2,636 ms. En el tramo estable de 60 s con 500 VU, hubo 16,180 solicitudes correctas, promedio 1,845.79 ms, p95 2,221 ms, máximo 2,636 ms. El intento previo con duración total de 60 s se conserva en el historial, pero no contaba con un minuto completo en concurrencia plena. Un intento inicial con el perfil Docker de 16 trabajadores y código montado desde Windows tuvo 54.9% de fallas por timeout; también se conserva en el historial. Los resultados son locales, dependen del hardware y no certifican rendimiento de producción ni SLA.

El archivo `database/aquarium-local.sqlite` queda como respaldo histórico y no es la base que usa el arranque normal. ## Acciones para cerrar fase cero

1. A fecha 21/10/2026, por solicitud del usuario, el sitio local y los contenedores están apagados. Se ejecutó `docker compose down` sin `-v`: los contenedores se quitaron, pero los volúmenes nombrados `aquarium_aquarium-postgres-data` y `aquarium_aquarium-redis-data` se conservaron. Los puertos 8000, 8001, 5173, 5432, 6379 y 8080 quedaron sin procesos escuchando. Para reanudar en PowerShell: `docker compose up -d postgres redis` y luego `.\scripts\serve-local.ps1` (Vite solo si se va a trabajar en frontend: `npm run dev -- --host 127.0.0.1`). No ejecutar `docker compose down -v` si se desean conservar los datos.
2. Mantener reproducible la versión y extensiones PHP para todos los desarrolladores; el lanzador local carga módulos requeridos en este equipo.
3. Terminar la matriz de trazabilidad QU4 → módulos → casos → evidencias.
4. La configuración local multiworker y la prueba sostenida de 500 VU ya están completadas. Mantener separadas las mediciones del servidor de desarrollo (8001) y del perfil Docker/Nginx/PHP-FPM (8080); ambos puertos son para uso local.
5. Las cinco cuentas de prueba solicitadas (cliente, administrador, almacenista, cajero POS y veterinario) ya están creadas en la base PostgreSQL local. Las credenciales son exclusivas del entorno local y se entregaron al usuario. Mantener pagos simulados y correo externo desactivado; las tarifas ilustrativas siguen sujetas a aprobación antes de tratarlas como reglas de producción.
